# 技術文書の構造設計

説明・仕様・操作条件の置き場所と参照経路を選ぶ判断基準を提供する。依頼と資料から読者・用途・今回解消する問題を捉え、初担当者が全体像を理解でき、経験者が必要な仕様・条件へ直接たどれる文書を作る。読者や用途が指定されている場合は、それに合わせる。

## 構造の選び方

文書の役割から、今回答えるべき問いを選ぶ。仕様を定める部分では動作・入出力・条件・例外・期待する結果、設計を説明する部分では境界・責務・依存・状態と重要な選択理由を扱う。目的・適用範囲・前提も、読者の判断を左右する場合に明らかにする。一文書で仕様と設計の両方を扱ってよい。

理解・判断・実装に必要な情報は落とさず、結論・要点と条件がすぐ分かる言葉と順序で書く。重複や回りくどい説明を省き、長文が続く場合は段落・箇条書き・表などで整理する。短くするために必要な説明を省略しない。

| 状況 | 適用する構造 | 適用の境界 |
|---|---|---|
| 全体像の説明と、個別仕様の参照が必要 | 概要から仕様の定義元へつなぐ。要約にも結論を左右する条件を残す | 短ければ一文書の見出しで足りる。説明が独立して必要な場合だけ分割し、仕様の定義元は一つにする |
| 途中の節では操作・判断に必要な前提が分からない | 必要条件を短く再掲するか、条件の具体的な名前で定義元へ直接リンクする | 冒頭や前節の記憶に依存させず、全文も再掲しない。操作値は読者が持つ情報から取得・選択・指定までつながるかを見る |
| 操作・非同期処理で状態が次の判断を左右する | 受付・処理中・完了・失敗・結果未確認を、仕様に存在する区別に従って、次の操作・待機・停止・再開条件へつなぐ | 仕様にない状態や復旧手順を増やさない。判断が変わるシステム固有の用語は定義か参照を置く |
| 関係・処理順序・条件を文章だけでは捉えにくい | 読者が理解・判断したいことから、本文・表・図の分担と図の種類・範囲を選ぶ。関係は構成図、順序はシーケンス図、条件の比較は表が候補になる | 省略・集約は、責務・順序・条件を誤解させない範囲に限る。構成要素・処理・状態の区別と、箱・矢印の意味を明確にする。正確な条件は定義元に置き、用語をそろえて重複を避ける。実際の表示サイズで縦横比・文字量・余白を確認し、読みにくければ向きだけでなく範囲・表現を選び直す |

これらは固定の章立てや必須工程ではない。新規作成では説明の骨組みに使い、既存改善では実際につまずく箇所とその参照先を対象にする。既存の形式・参照先を変える必要がなければ維持する。

## 配置の問題と仕様不足を分ける

情報が既に定義されているなら、その場所への導線を直す。資料にない動作・条件・保証・選択理由は、説明を成立させるために補わず、資料不足か設計上の未決事項かを区別する。新しい仕様の提案が依頼に含まれる場合も、確定仕様と分ける。

例えば、タイムアウト後の再試行仕様が別節にあるなら、操作の説明からその条件へつなぐ。仕様自体がなければ、安全に再試行できると断定せず、必要な設計判断を示す。

## 成果物と終了

標準の成果物は依頼された文書そのものとする。本文には対象の仕組み・仕様・必要な判断を書き、構成の狙いや編集実況を混ぜない。

解消したかった問いに、完成文書と明示参照から答えられるか確認する。答えられない箇所だけ直し、元の意味・条件・保証を保つ。仕様不足を示せたことと、操作可能になったことは区別する。

今回必要な理解・参照が成立したら終了する。依頼範囲外の保証が必要になった場合は、その不足と判断への影響を示し、前提の証明へ確認範囲を広げない。
